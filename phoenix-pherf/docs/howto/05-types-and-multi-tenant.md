# How to cover Phoenix types and multi-tenant workloads

## The question

This guide addresses two central design questions that arise when evaluating schema data types and
multi-tenant architectures.

1. Do the newer Phoenix data types (FLOAT ARRAY, DOUBLE ARRAY, VARBINARY_ENCODED, JSON, and BSON)
   load and query accurately through Pherf, and what is the per-row execution overhead of evaluating
   a document function relative to a plain scan across the same dataset?
2. When numerous tenants share a single multi-tenant table, how does the concurrent execution of a
   single high-volume tenant (a noisy neighbour) affect the operation latency experienced by smaller
   tenants?

## Before you start

**Audience.** This guide is intended for prospective users whose schemas incorporate documents,
arrays, binary keys, or multi-tenant views, as well as Phoenix developers modifying the type
system, document functions, or tenant view implementation.

**Prerequisites.**

- Complete the build and generate `$PX_OUT/howto/pherf-env.sh` by following steps 2 and 3 of
  [HOWTO 01](01-first-pherf-run.md).
- Ensure access to a running cluster deployed with the Phoenix server from this source tree, along
  with its ZooKeeper quorum address.
- Install `jq` for parsing JSON output reports.
- Review [HOWTO 02](02-scenario-authoring-and-validation.md) for background on the offline
  validation workflow.

| Cost | Value |
|---|---|
| Wall time | Approximately 20 minutes, depending on cluster capacity and responsiveness. |
| Memory | Up to 3 GiB of heap memory for the Pherf JVM on the client host. |
| Disk | Less than 20 MiB of disk space for generated result artifacts. |
| Files written | `$HOWTO/*.xml`, `$HOWTO/conf/datamodel/howto_mt.sql`, `$HOWTO/*.log`, and
`$HOWTO/work/RESULTS*` on disk, plus the Phoenix tables `PHERF.HOWTO_TYPES`, `PHERF.HOWTO_MT`
(including its tenant views), `PHERF.REF_JSON`, and `PHERF.REF_BSON`. |

The offline validation steps were executed directly, and their actual output excerpts are captured
below. The execution steps that require a live cluster were verified against the implementation
source code rather than executed on a cluster for this guide; those output excerpts are labeled as
"expected".

## Method

### Types

**Hypothesis.** Every new data type completes a full write-and-read round trip accurately: the data
load inserts 10,000 rows, and each aggregate count query returns the exact row count guaranteed by
the generation rules. Furthermore, evaluating a filter predicate on a document field incurs a
measurably higher per-row cost than executing a plain count across the same rows.

**How Pherf makes the values.**

| Type | `length` | `minValue`, `maxValue` | A `LIST` value | Binding |
|---|---|---|---|---|
| `FLOAT_ARRAY`, `DOUBLE_ARRAY` | Defines the number of elements in the array. | Defines the
numeric bounds for each generated element. | Represents a single element; all list entries combine
to form one array. | Bound as a SQL array instance. |
| `VARBINARY_ENCODED` | Defines the number of generated bytes. | - | Specified as hexadecimal text,
such as `00ff00`. | Bound via `setBytes` on the decoded hexadecimal bytes so that 0x00 and 0xFF
bytes survive intact. |
| `JSON`, `BSON` | Defines the character length of the generated string fields. | - | Specified as
a full document formatted as JSON text. | Bound as JSON text; BSON columns also bind values
formatted as JSON text. |

A `RANDOM` document follows a deterministic structural schema so that queries can target predictable
document paths:
`{"s": text, "n": int, "d": double, "b": boolean, "a": [3 ints], "o": {"s": text, "n": int}}`.
When a rule defines a `prefix`, that prefix forms the leading characters of the top-level field `s`.
Note that Pherf rule type names use an underscore (`FLOAT_ARRAY`), whereas Phoenix SQL type names
use a space (`FLOAT ARRAY`).

**Rule limits.** Configuring `SEQUENTIAL` data generation on `FLOAT_ARRAY`, `DOUBLE_ARRAY`, or
`VARBINARY_ENCODED` produces an error under both rule-based generators and co-generation. Using
`SEQUENTIAL` on `JSON` and `BSON` requires an explicit value list because a simple numeric counter
does not form a valid document. Under co-generation, an array rule must also specify both `minValue`
and `maxValue`. Vector types remain out of scope for this guide.

**The bson jar.** In this source tree, the Phoenix embedded and lite client JARs do not bundle the
`org.bson` package. Because Phoenix stores every JSON value internally as BSON, any client using
those JARs must include `bson-<version>.jar` on its class path even when the schema contains no BSON
or JSON columns. Standard Maven and Gradle builds resolve this artifact automatically as a
transitive dependency, whereas manually constructed class paths must include it explicitly, as
`pherf-env.sh` does. If the JAR is omitted, the client fails with
`NoClassDefFoundError: org/bson/BsonReader` (which manifests even when running `-validate` against
the relational reference scenario that contains no document columns) or subsequently fails with
`Could not initialize class` for `PJson`.

**Controls.** The experiment performs a single data load followed by all query executions against
that identical set of rows. Every query operates over the same 10,000-row dataset, and warmup
iterations run prior to the measured executions.

**What to measure and why.** Compare the `steady` phase p50 latency of `count` (which performs a
plain full scan) against the `steady` phase p50 latencies of `jsonPrefix` and `bsonFilter` (which
perform the same scan while evaluating a document extraction function on each row). Dividing the
latency difference by the total row count yields an estimate of the per-row evaluation cost of the
document function. Setting `expectedAggregateRowCount` on the count queries converts any row-count
mismatch into an explicit execution error, ensuring that parameter-binding defects cannot pass
silently.

**What invalidates the result.** The measurement is invalidated if the log records a row-count
mismatch error, if any query records fewer histogram samples than its configured number of
executions, or if a region move occurs during the measurement window.

### Tenants

**How Pherf binds tenants.**

- Setting `tenantId` on a scenario binds the scenario DDL statements, the data load phase, and every
  query in that scenario to a tenant-specific connection.
- Setting `tenantId` on an individual query overrides the scenario-level tenant binding for that
  specific query.
- Setting `useGlobalConnection="true"` on a query or DDL element forces execution over a global,
  non-tenant connection.
- The `ddl` attribute configured on a query executes prior to its enclosing query set using that
  query's tenant connection; use this mechanism to create the tenant view required by that tenant.
- Specifying `<phoenixProperties>` on a query set overrides matching scenario property keys for the
  query connections belonging to that query set only. Only standard performance runs using the thick
  driver apply these query-set properties; `-diff`, the thin driver, and `-mt` workloads ignore
  them.

**The `-mt` load profile.** When invoked with `-mt`, Pherf executes any scenario containing a
`loadProfile` as a continuous stream of tenant operations:

- `tenantDistribution` elements define tenant groups by specifying an `id`, a selection `weight`,
  and `numTenants`. Pherf selects a tenant group according to its weight and then chooses a tenant
  uniformly at random within that group. The generated tenant identifier consists of `T`, followed
  by the group identifier left-padded with `x` to 6 characters, followed by an 8-digit zero-based
  index: for example, the `light` group produces tenant identifiers ranging from `Txlight00000000`
  to `Txlight00000199`. Setting `useGlobalConnection="true"` on a tenant group directs its
  operations to a global connection.
- `opDistribution` elements determine operation selection by weight. Each operation identifier
  references an `upsert`, a `query`, an `idleTime`, or a `udf` defined within the scenario. The
  `batchSize` element specifies the number of rows written per upsert operation, while
  `numOperations` defines the total number of operations executed for the scenario.
- The `generatorName` attribute selects the distribution strategy and accepts `WEIGHTED`, `UNIFORM`,
  or `SEQUENTIAL`.
- Before executing the first operation for a given tenant, Pherf runs the scenario's
  `preScenarioDdls` once on that tenant's connection. If DDL initialization fails 3 times, the
  workload aborts with `Could not initialize tenant after 3 attempts`, reporting both the tenant and
  the view. Because these DDL statements execute synchronously on the thread publishing the
  operation stream, initializing each new tenant introduces a pause in that scenario's stream.
- Each scenario runs `pherf.mt.handlers_per_scenario` concurrent handler threads (default 4), with
  each worker processing operations as rapidly as possible in a closed loop without rate limiting.
- Every scenario included in the run launches its own independent operation stream, and all active
  scenarios execute concurrently. Passing `-scenarioName` restricts execution to a single named
  scenario.
- Latency histograms record operations under the key `operation:<scenario>:<operation id>`, which
  aggregates measurements across all tenants within that scenario. Note that legacy XML result files
  do not include `-mt` metrics.
- Individual operations open their Phoenix connections using only the tenant identifier. Scenario
  `phoenixProperties` supply the `pherf.mt.*` engine configuration keys, and Pherf merges those
  entries into shared properties visible to subsequent scenarios in the same run; consequently, you
  should configure identical `pherf.mt.*` keys across all scenarios.
- The `-mt` runner rejects any scenario configured with `coGeneration`, does not support a `mix`,
  and ignores command-line launch overrides. Queries configured with `kind="SCAN"` or
  `kind="DELETE"` execute using the standard data-generation rules.

A complete reference example of a multi-tenant load profile is available in
[test_mt_workload_template.xml](../../src/test/resources/scenario/test_mt_workload_template.xml).

**Hypothesis.** The p50 and p99 operation latencies experienced by the 200 light tenants remain
unchanged regardless of whether the heavy tenant executes concurrently. Any latency increase that
exceeds the natural variance across replicate runs indicates cross-tenant interference.

**The experiment.** Placing the `light` workload in its own dedicated scenario isolates its latency
metrics under distinct histogram keys. Run A executes the `light` scenario in isolation
(`-scenarioName light`). Run B executes both `light` and `heavy` concurrently. Because `heavy` is
configured with 4 times the total operation count of `light`, the heavy workload remains active
throughout the entire duration of the `light` run. The net interference is measured as the latency
of `light` in run B minus its baseline latency in run A.

**Controls.** Maintain a consistent initial table state before runs A and B by either executing each
run against a freshly created table or accepting that run B accumulates rows from `heavy` and
alternating execution in an A, B, A, B sequence. Keep the total operation count for `light`
constant across runs. Pre-create all 200 light tenant views by running `light` once as an unmeasured
warmup pass so that view creation DDL overhead does not contaminate the measured samples.

**Noise.** Because tenant selection is randomized without a fixed seed, the exact operation counts
assigned to each tenant group vary within statistical sampling error. In addition, the `count`
query executed by the heavy tenant scans an expanding set of rows as its upsert operations
accumulate data.

**Fairness questions to ask.**

- Does the p99 latency of the light tenants increase as the heavy tenant's workload share grows?
- Does the heavy tenant saturate the RegionServer hosting its key range? Because the tenant
  identifier forms the leading primary key column of a multi-tenant table, a single tenant's rows
  are concentrated within a small number of regions. You can evaluate read skew by configuring
  `pherf.verdict.serverJmx` (which requires at least 2 RegionServers and a read window of at least
  60 s; see [VERDICT.md](../../VERDICT.md)).
- What is the cumulative overhead of executing tenant view DDLs as the tenant population scales?
  Compare the initial cold execution of `light` (which creates the tenant views) against the
  subsequent warm execution.
- Does enabling the connection cache improve performance? Because the cache key incorporates the
  tenant identifier, running 200 distinct tenants against a pool capped at
  `pherf.default.threadpool` idle connections (default 10) causes most connection leases to miss the
  cache.
- To inspect latency broken down by individual tenant group, register a custom metrics sink: each
  emitted `operation` record includes the `tenant` and `tenant_group` tags
  ([HOWTO 07](07-extending-pherf.md)).

## Steps

### Types

1. Execute the environment initialization commands from the root of the repository, switch to the
   working directory, and configure the ZooKeeper quorum address for your cluster.

   ```sh
   export PX_OUT="${PX_OUT:-$HOME/phoenix-harness}"
   HOWTO="$PX_OUT/howto/p05"; mkdir -p "$HOWTO/work"
   . "$PX_OUT/howto/pherf-env.sh"
   cd "$HOWTO/work"
   ZK="zk1.example.com,zk2.example.com,zk3.example.com:2181"
   ```

2. Create the types scenario file. Because the scenario includes a pre-scenario DDL statement that
   creates the target table directly, the execution does not require a separate schema file.

   ```sh
   cat > "$HOWTO/types_scenario.xml" <<'EOF'
   <?xml version="1.0" encoding="UTF-8"?>
   <datamodel name="howto_types">
     <datamapping>
       <column>
         <type>VARCHAR</type>
         <userDefined>true</userDefined>
         <dataSequence>SEQUENTIAL</dataSequence>
         <length>12</length>
         <prefix>id</prefix>
         <name>ID</name>
       </column>
       <!-- Arrays: length is the element count; each element is in [minValue, maxValue]. -->
       <column>
         <type>FLOAT_ARRAY</type>
         <userDefined>true</userDefined>
         <dataSequence>RANDOM</dataSequence>
         <length>4</length>
         <minValue>-100</minValue>
         <maxValue>100</maxValue>
         <name>FA</name>
       </column>
       <column>
         <type>DOUBLE_ARRAY</type>
         <userDefined>true</userDefined>
         <dataSequence>RANDOM</dataSequence>
         <length>8</length>
         <minValue>0</minValue>
         <maxValue>1000</maxValue>
         <name>DA</name>
       </column>
       <!-- VARBINARY_ENCODED: length is the byte count; a LIST value is hex text. -->
       <column>
         <type>VARBINARY_ENCODED</type>
         <userDefined>true</userDefined>
         <dataSequence>RANDOM</dataSequence>
         <length>32</length>
         <name>PAYLOAD</name>
       </column>
       <column>
         <type>VARBINARY_ENCODED</type>
         <userDefined>true</userDefined>
         <dataSequence>LIST</dataSequence>
         <name>TAG</name>
         <valuelist>
           <datavalue distribution="90"><value>00ff00</value></datavalue>
           <datavalue distribution="10"><value>0a</value></datavalue>
         </valuelist>
       </column>
       <!-- JSON and BSON: a RANDOM document has the shape {s,n,d,b,a[3],o{s,n}}; length is the
            length of the string fields s and o.s. -->
       <column>
         <type>JSON</type>
         <userDefined>true</userDefined>
         <dataSequence>RANDOM</dataSequence>
         <length>8</length>
         <prefix>j</prefix>
         <name>JDOC</name>
       </column>
       <column>
         <type>BSON</type>
         <userDefined>true</userDefined>
         <dataSequence>RANDOM</dataSequence>
         <length>8</length>
         <name>BDOC</name>
       </column>
     </datamapping>
     <scenarios>
       <scenario tableName="PHERF.HOWTO_TYPES" rowCount="10000" name="types">
         <preScenarioDdls>
           <ddl tableName="PHERF.HOWTO_TYPES"
                statement="CREATE TABLE IF NOT EXISTS ? (ID VARCHAR NOT NULL PRIMARY KEY,
                  FA FLOAT ARRAY, DA DOUBLE ARRAY, PAYLOAD VARBINARY_ENCODED,
                  TAG VARBINARY_ENCODED, JDOC JSON, BDOC BSON)"/>
         </preScenarioDdls>
         <querySet concurrency="1" executionType="SERIAL" numberOfExecutions="100"
                   warmupExecutions="5">
           <query id="count" expectedAggregateRowCount="10000"
                  statement="SELECT COUNT(*) FROM PHERF.HOWTO_TYPES"/>
           <query id="jsonPrefix" expectedAggregateRowCount="10000"
                  statement="SELECT COUNT(*) FROM PHERF.HOWTO_TYPES
                    WHERE JSON_VALUE(JDOC, '$.s') LIKE 'j%'"/>
           <query id="jsonNested"
                  statement="SELECT JSON_VALUE(JDOC, '$.o.s') FROM PHERF.HOWTO_TYPES LIMIT 100"/>
           <query id="bsonFilter" expectedAggregateRowCount="10000"
                  statement="SELECT COUNT(*) FROM PHERF.HOWTO_TYPES
                    WHERE BSON_VALUE(BDOC, 's', 'VARCHAR') IS NOT NULL"/>
           <query id="bsonNested"
                  statement="SELECT BSON_VALUE(BDOC, 'o.n', 'INTEGER') FROM PHERF.HOWTO_TYPES
                    LIMIT 100"/>
           <query id="arrayLength" expectedAggregateRowCount="10000"
                  statement="SELECT COUNT(*) FROM PHERF.HOWTO_TYPES WHERE ARRAY_LENGTH(DA) = 8"/>
           <query id="binaryTag"
                  statement="SELECT COUNT(*) FROM PHERF.HOWTO_TYPES WHERE TAG = X'0a'"/>
         </querySet>
       </scenario>
     </scenarios>
   </datamodel>
   EOF
   ```

   In this scenario, every generated `s` field begins with the prefix `j`, every document contains
   the field `s`, and every `DA` array contains exactly 8 elements. Consequently, the `jsonPrefix`,
   `bsonFilter`, and `arrayLength` queries must each count all 10,000 rows. Approximately 10% of the
   rows receive the binary tag `0a`. Pherf automatically treats any SQL statement containing
   `COUNT(` as an aggregate count query and reads the total row count from the first column of the
   returned result set.

3. Validate the scenario file offline.

   ```sh
   pherf -validate -disableSchemaApply -label types -scenarioFile "$HOWTO/types_scenario.xml" \
     2>"$HOWTO/types-validate.log"
   ```

   Captured output:

   ```text
   Validation: 0 error(s) in 1 file(s). Report: RESULTS/VALIDATION_types.json
   ```

4. Drop any existing copy of the table, load the generated rows, and execute the query set.

   ```sh
   pherf -z "$ZK" -drop 'PHERF\.HOWTO_TYPES' -l -q -disableSchemaApply -connectionCache \
     -label types1 -scenarioFile "$HOWTO/types_scenario.xml" 2>"$HOWTO/types1.log"
   echo "exit=$?"
   grep -c 'does not match expected' "$HOWTO/types1.log"
   ```

   Expected output (not captured on a live cluster):

   ```text
   exit=0
   0
   ```

5. Compare the latency of the document filter queries against the plain count query.

   ```sh
   jq -r '.histograms[] | select(.phase == "steady")
     | [.operation, .count, .p50Us, .p99Us] | @tsv' RESULTS_HDR/LATENCY_types1.json
   ```

   Expected output shape (not captured; latency values are illustrative):

   ```text
   query:types:arrayLength  100  ...
   query:types:binaryTag    100  ...
   query:types:bsonFilter   100  ...
   query:types:bsonNested   100  ...
   query:types:count        100  ...
   query:types:jsonNested   100  ...
   query:types:jsonPrefix   100  ...
   ```

   Every operation key must record 100 samples. You can estimate the per-row evaluation cost of
   `JSON_VALUE` as `(p50 of jsonPrefix - p50 of count) / 10000`, and calculate the per-row cost of
   `bsonFilter` in the same manner.

6. Execute the co-generated reference scenarios for JSON and BSON. Each reference scenario loads
   1000 rows and drives an open-loop workload consisting of point lookups, range scans, and range
   deletes that evaluate a document path on every read (see
   [HOWTO 03](03-open-loop-profiles-and-mixes.md) and [HOWTO 04](04-co-generation.md) for details on
   workload profiles and co-generation). The corresponding smoke profile resides alongside each
   scenario file.

   ```sh
   for s in json bson; do
     pherf -z "$ZK" -l -q -disableSchemaApply -label "ref-$s" \
       -scenarioFile "$PHX_ROOT/phoenix-pherf/config/reference/${s}_scenario.xml" \
       2>"$HOWTO/ref-$s.log" || echo "ref-$s failed"
   done
   jq -r '.schedules[] | [.scenario, .scheduled, .completed, .dropped, .aborted] | @tsv' \
     RESULTS_HDR/LATENCY_ref-json.json RESULTS_HDR/LATENCY_ref-bson.json
   ```

   Expected output (not captured on a live cluster; operation counts are derived from the profile
   definitions documented in [README.md](../../README.md)):

   ```text
   referenceJson  60  60  0  0
   referenceBson  60  60  0  0
   ```

   Upon completion, 520 rows remain in `PHERF.REF_JSON` and 700 rows remain in `PHERF.REF_BSON`
   because the DELETE operations remove contiguous blocks of rows. Running the workload again with
   `-l` reloads the missing rows.

### Tenants

7. Create the SQL schema definition for the multi-tenant base table, declaring the tenant identifier
   as the leading primary key column.

   ```sh
   mkdir -p "$HOWTO/conf/datamodel"
   cat > "$HOWTO/conf/datamodel/howto_mt.sql" <<'EOF'
   CREATE TABLE IF NOT EXISTS PHERF.HOWTO_MT (
       TENANT_ID CHAR(15) NOT NULL,
       ID CHAR(15) NOT NULL,
       V VARCHAR,
       N INTEGER
       CONSTRAINT PK PRIMARY KEY (TENANT_ID, ID)) MULTI_TENANT=true
   EOF
   ```

8. Create a scenario that verifies tenant connection binding. The data load phase inserts 10,000
   rows through the tenant view belonging to `TNT000000000001`. The `own` query executes under that
   same tenant and must observe all 10,000 rows, whereas the `other` query executes under a second
   tenant and must observe 0 rows, confirming tenant isolation.

   ```sh
   cat > "$HOWTO/tenant_scenario.xml" <<'EOF'
   <?xml version="1.0" encoding="UTF-8"?>
   <datamodel name="howto_tenant">
     <datamapping>
       <column>
         <type>CHAR</type>
         <dataSequence>RANDOM</dataSequence>
         <length>15</length>
         <name>GENERAL_CHAR</name>
       </column>
       <column>
         <type>VARCHAR</type>
         <dataSequence>RANDOM</dataSequence>
         <length>20</length>
         <name>GENERAL_VARCHAR</name>
       </column>
       <column>
         <type>INTEGER</type>
         <dataSequence>RANDOM</dataSequence>
         <minValue>1</minValue>
         <maxValue>1000</maxValue>
         <name>GENERAL_INTEGER</name>
       </column>
     </datamapping>
     <scenarios>
       <!-- The scenario DDL and the data load run as tenant TNT000000000001. -->
       <scenario tableName="PHERF.HOWTO_TV" tenantId="TNT000000000001" rowCount="10000"
                 name="oneTenant">
         <preScenarioDdls>
           <ddl statement="CREATE VIEW IF NOT EXISTS PHERF.HOWTO_TV AS
             SELECT * FROM PHERF.HOWTO_MT"/>
         </preScenarioDdls>
         <querySet concurrency="1" executionType="SERIAL" numberOfExecutions="100"
                   warmupExecutions="10">
           <!-- These properties apply to the connections of this query set only. -->
           <phoenixProperties>
             <entry>
               <key>phoenix.query.timeoutMs</key>
               <value>30000</value>
             </entry>
           </phoenixProperties>
           <!-- Runs as the scenario tenant. -->
           <query id="own" expectedAggregateRowCount="10000"
                  statement="SELECT COUNT(*) FROM PHERF.HOWTO_TV"/>
           <!-- Runs as another tenant. Its ddl makes the view of that tenant first. -->
           <query id="other" expectedAggregateRowCount="0" tenantId="TNT000000000002"
                  ddl="CREATE VIEW IF NOT EXISTS PHERF.HOWTO_TV AS SELECT * FROM PHERF.HOWTO_MT"
                  statement="SELECT COUNT(*) FROM PHERF.HOWTO_TV"/>
           <!-- Runs on a global connection: the tenants that have rows. -->
           <query id="all" useGlobalConnection="true"
                  statement="SELECT COUNT(DISTINCT TENANT_ID) FROM PHERF.HOWTO_MT"/>
         </querySet>
       </scenario>
     </scenarios>
   </datamodel>
   EOF
   ```

9. Create the `-mt` workload scenario defining one heavy tenant and 200 light tenants, placing each
   tenant class in a separate scenario definition so that their latency histograms are recorded
   under distinct keys.

   ```sh
   cat > "$HOWTO/mt_scenario.xml" <<'EOF'
   <?xml version="1.0" encoding="UTF-8"?>
   <datamodel name="howto_mt">
     <datamapping>
       <column>
         <type>CHAR</type>
         <dataSequence>RANDOM</dataSequence>
         <length>15</length>
         <name>GENERAL_CHAR</name>
       </column>
       <column>
         <type>VARCHAR</type>
         <dataSequence>RANDOM</dataSequence>
         <length>20</length>
         <name>GENERAL_VARCHAR</name>
       </column>
       <column>
         <type>INTEGER</type>
         <dataSequence>RANDOM</dataSequence>
         <minValue>1</minValue>
         <maxValue>1000</maxValue>
         <name>GENERAL_INTEGER</name>
       </column>
     </datamapping>
     <scenarios>
       <!-- The noisy neighbour: one tenant with many operations. -->
       <scenario tableName="PHERF.HOWTO_MT_VIEW" name="heavy" generatorName="WEIGHTED">
         <loadProfile>
           <batchSize>100</batchSize>
           <numOperations>40000</numOperations>
           <tenantDistribution id="heavy" weight="100" numTenants="1"/>
           <opDistribution id="write" weight="50"/>
           <opDistribution id="count" weight="25"/>
           <opDistribution id="page" weight="25"/>
         </loadProfile>
         <preScenarioDdls>
           <ddl statement="CREATE VIEW IF NOT EXISTS PHERF.HOWTO_MT_VIEW AS
             SELECT * FROM PHERF.HOWTO_MT"/>
         </preScenarioDdls>
         <upserts>
           <upsert id="write">
             <column><type>CHAR</type><name>ID</name></column>
             <column><type>VARCHAR</type><name>V</name></column>
             <column><type>INTEGER</type><name>N</name></column>
           </upsert>
         </upserts>
         <querySet>
           <query id="count" statement="SELECT COUNT(*) FROM PHERF.HOWTO_MT_VIEW"/>
           <query id="page" statement="SELECT ID, V FROM PHERF.HOWTO_MT_VIEW LIMIT 20"/>
         </querySet>
       </scenario>
       <!-- The tenants under test: 200 light tenants. -->
       <scenario tableName="PHERF.HOWTO_MT_VIEW" name="light" generatorName="WEIGHTED">
         <loadProfile>
           <batchSize>10</batchSize>
           <numOperations>10000</numOperations>
           <tenantDistribution id="light" weight="100" numTenants="200"/>
           <opDistribution id="write" weight="40"/>
           <opDistribution id="count" weight="30"/>
           <opDistribution id="page" weight="30"/>
         </loadProfile>
         <preScenarioDdls>
           <ddl statement="CREATE VIEW IF NOT EXISTS PHERF.HOWTO_MT_VIEW AS
             SELECT * FROM PHERF.HOWTO_MT"/>
         </preScenarioDdls>
         <upserts>
           <upsert id="write">
   ```

## Read the result

- **Types.** Any aggregate query that does not return 10,000 rows logs an error containing
  `does not match expected` and omits that execution from the latency histogram samples. If an
  operation key is entirely absent from the report, every execution of that query failed and you
  should inspect the execution log for the underlying exception. The per-row evaluation overhead of
  a document function equals the p50 latency difference relative to `count` divided across the
  scanned rows. Because this scenario does not define a functional index on the queried JSON or BSON
  document paths, Phoenix evaluates the document extraction function on every scanned row.
- **Tenants.** The `own` and `other` query results verify that a tenant-bound connection accesses
  only data belonging to its own tenant view. To evaluate noisy-neighbour interference, compare the
  p50 and p99 latencies of each `operation:light:*` key between run A and run B. Any run B latency
  that exceeds the variation range observed across the run A replicates indicates cross-tenant
  interference. To identify the contended resource—whether RegionServer RPC handlers, the block
  cache, or the specific region hosting the heavy tenant's key range—correlate the run window with
  server-side cluster telemetry rather than relying solely on client-side Pherf metrics.
- **Limits.** The `-mt` execution engine operates as a closed loop driven by 4 concurrent worker
  handlers per scenario. Consequently, it measures contention under the saturation load generated by
  those worker threads rather than at a fixed arrival rate. To evaluate multi-tenant behavior at a
  controlled request rate, configure an open-loop query set
  ([HOWTO 03](03-open-loop-profiles-and-mixes.md)) and bind one tenant to each query set.

## Reproduce it

To make a run reproducible, archive the Git commit hash of the source tree, the deployed cluster
component versions, the scenario and schema files under `$HOWTO`, the run labels, and the generated
`RESULTS` and `RESULTS_HDR` output directories. Because standard rule-based data generation and
`-mt` tenant selection do not use a fixed random seed, repeating those runs produces different row
values and tenant execution sequences drawn from the same statistical distributions. By contrast,
the reference scenarios use deterministic co-generation with a fixed seed, producing identical data
values across repeated runs.

## Clean up

Drop all tables created during this guide. Because Pherf executes drops with `CASCADE`, dropping the
base table automatically removes all associated tenant views.

```sh
pherf -z "$ZK" -disableSchemaApply \
  -drop 'PHERF\.(HOWTO_TYPES|HOWTO_MT|REF_JSON|REF_BSON)' 2>"$HOWTO/drop.log"
echo "exit=$?"
```

Expected output (not captured on a live cluster): `exit=0`.
